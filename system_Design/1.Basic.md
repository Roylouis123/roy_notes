# System Design — Requirement & Estimation Cheat Sheet

## 🧠 The Big Picture

Before designing anything, think:

> **WHAT → HOW WELL → LIMITS → LOAD → DATA → INFRA**

```text
Functional
    ↓
Non-Functional
    ↓
Constraints
    ↓
Traffic Estimation
    ↓
Storage Estimation
    ↓
Capacity Estimation
```

---

## 1. Functional Requirements

### What?

**What must the system DO?**

These are the features/actions of the system.

Examples:

```text
Food Delivery
→ Login
→ Search restaurant
→ Add food to cart
→ Place order
→ Make payment
→ Track order
```

🧠 **Remember:**  
> Functional = **WHAT the system does**

---

## 2. Non-Functional Requirements

### What?

**How WELL must the system work?**

Common NFRs:

| Requirement | Question |
|---|---|
| **Performance** | How fast? |
| **Scalability** | How much can it grow? |
| **Availability** | How often should it be available? |
| **Reliability** | Can we trust it not to lose/fail data? |
| **Security** | Who can access what? |
| **Consistency** | How quickly should data stay synchronized? |

Example:

```text
API response < 300 ms
Availability = 99.99%
Support = 1M concurrent users
```

🧠 **Remember:**

> Functional = **WHAT**  
> Non-functional = **HOW WELL**

---

# 3. Constraints

### What?

**What limits our solution?**

Typical constraints:

```text
💰 Budget
👨‍💻 Team size
⏰ Deadline
☁️ Cloud / technology restrictions
🌍 Data location
📈 Expected growth
🔒 Security / compliance
```

Example:

> "Must handle 1M users, but budget is only ₹50K/month."

That constraint affects your architecture.

🧠 **Remember:**

> Constraint = **What can restrict our design?**

---

# 4. Traffic Estimation

### What?

**How much traffic will the system receive?**

Start with:

```text
DAU = Daily Active Users
```

Then:

### Daily Requests

```text
DAU × Requests/User/Day
```

### Average QPS

```text
Daily Requests ÷ 86,400
```

### Peak QPS

```text
Average QPS × Peak Factor
```

Also estimate:

```text
Read traffic
Write traffic
```

### Example

```text
DAU = 1M
Requests/user/day = 20

Daily requests
= 1M × 20
= 20M

Average QPS
= 20M ÷ 86,400
≈ 231 QPS

If peak = 5×:

Peak QPS
≈ 1,155 QPS
```

🧠 **Remember:**

> **Users → Requests → QPS → Peak QPS**

---

# 5. Storage Estimation

### What?

**How much data will the system generate?**

Basic formula:

```text
Daily Storage
=
Objects/day × Size/object
```

Then:

```text
Yearly Storage
=
Daily Storage × 365
```

Don't forget:

```text
Raw Data
+ Indexes
+ Replicas
+ Backups
+ Logs
```

### Example

```text
2M posts/day
× 2 KB/post
= 4 GB/day

4 GB × 365
≈ 1.46 TB/year
```

🧠 **Remember:**

> **Objects → Size → Daily → Yearly → Overhead**

---

# 6. Capacity Estimation

### What?

**How much infrastructure do we need to handle the load?**

Example:

```text
Peak traffic = 10,000 QPS

One server safely handles = 1,000 QPS

10,000 ÷ 1,000
= 10 servers
```

But don't run exactly 10.

Add **headroom** for:

- Traffic spikes
- Server failures
- Deployments
- Future growth

So you might provision around:

```text
10 × 1.5 = 15 servers
```

Real capacity planning also considers:

```text
CPU
RAM
Network
Database
Cache
Storage
```

🧠 **Remember:**

> **Load → Resource capacity → Headroom → Infrastructure**

---

# 🔥 30-Second Revision

Whenever you see **"Design X"**, immediately think:

```text
1️⃣ Functional
   → What does it DO?

2️⃣ Non-functional
   → How WELL should it work?

3️⃣ Constraints
   → What LIMITS us?

4️⃣ Traffic
   → How much LOAD?
   → DAU → Requests → QPS → Peak QPS

5️⃣ Storage
   → How much DATA?
   → Objects × Size → Daily → Yearly

6️⃣ Capacity
   → How much INFRA?
   → Load ÷ Resource capacity + Headroom
```
